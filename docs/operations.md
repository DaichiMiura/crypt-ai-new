# Operations Policy

## Operating principle

運用の第一目的は、意図した固定バージョンが制限内で動いていることを確認し、そうでなければ安全に止めることである。

## Minimum monitoring

- プロセス稼働、最終heartbeat、データ鮮度、時計ずれ
- 注文送信、受付、拒否、取消、約定、未確定状態
- 取引所残高と内部台帳の差分
- ポジション、実現・未実現損益、手数料
- 注文頻度、価格乖離、スリッページ
- 日次損失、ドローダウン、リスク上限消費率
- デプロイ版、戦略設定、リスク設定

アラートが送れない状態も監視障害として扱い、新規リスクを増やさない。

## Binance Japan shadow operation

shadowではBinance Japanの市場データを本番相当の経路で受信するが、注文APIへ送信してはならない。戦略の出力は注文直前で止め、次の情報から想定約定を計算する。

- signal time、receive time、decision time、simulated order time
- best bid/ask、spread、板の厚さ、想定価格、数量、価格刻み、最小数量
- データ遅延、注文相当の処理時間、想定slippage、部分約定、未約定理由
- その時点のfee model、想定commission、口座残高を使わないpaper残高

Globalバックテストとの差は、損益だけでなく、価格basis、spread、fill rate、遅延、費用控除後の期待値、ドローダウンで確認する。shadowで観測した差を、Global proxyの欠陥、Japan venue固有の差、実装上の差に分類して記録する。

shadow用のAPIキーを作る場合も、読み取り専用権限を基本とし、`TRADE`や資金移動権限を付与しない。live注文経路を解禁する変更は、本方針の通常運用とは別の人間承認付き変更とする。

## Daily reconciliation

運用日ごとに次を照合する。

1. 取引所の注文・約定と内部イベント
2. 取引所残高と内部現金・ポジション
3. 手数料、資金調達料、入出金、調整額
4. 期待したシグナル・注文と実際の差
5. バックテストまたはペーパー想定との乖離

未照合差分を損益に埋め込まない。原因、暫定措置、解消を記録する。

## Incident response

次の場合は新規注文を停止し、必要なら未約定注文を安全に取り消す。

- 損失またはドローダウン上限到達
- 価格・残高・ポジションが不明または不一致
- データ停止、時計ずれ、異常スプレッド
- 重複注文、再試行の不整合、想定外の注文
- 認証情報漏洩の疑い
- 監視またはリスクエンジンの停止

復旧は「プロセスが起動した」だけでは完了しない。状態を再構築・照合し、原因と影響範囲を確認し、人間が再開を承認する。

## Review cadence

- 日次: 注文、約定、残高、損益、アラートの照合
- 週次: 戦略逸脱、コスト、データ品質、インシデント、未解決リスク
- 月次: 戦略継続・縮小・停止、資本配分、前提の陳腐化
- 変更時: 固定成果物、設定、監視、ロールバックの確認

振り返りでは損益と判断品質を分ける。利益の出た規則違反と、損失の出た正しい停止の両方を適切に評価する。
