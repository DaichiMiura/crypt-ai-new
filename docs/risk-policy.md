# Risk Policy

## Default posture

本番設定は取引不能とする。[config/risk-limits.yaml](../config/risk-limits.yaml) の上限はゼロであり、`live_trading_enabled` は `false` でなければならない。

Phase 0のペーパー運用では、実取引所へ接続しない専用アダプターだけが
[config/paper-risk-limits.yaml](../config/paper-risk-limits.yaml) を使える。この設定をlive用アダプターへ渡してはならない。ペーパー運用でも上限超過、古いデータ、照合失敗、不明状態は拒否する。

## Global limits and strategy budgets

`paper-risk-limits.yaml`は口座・環境全体のハード上限であり、戦略固有の適正値ではない。各戦略は、登録済み実験に対応する
`config/strategies/<strategy-id>-risk.yaml`でリスク予算を持つ。

実効値は、常に次の小さい方を使う。

```text
実効注文上限       = min(全体上限, 戦略上限)
実効ポジション上限 = min(全体上限, 戦略上限)
実効注文頻度       = min(全体上限, 戦略上限)
実効日次損失上限   = min(全体上限, 戦略上限)
```

全体上限は、戦略設定を誤って大きくしても超えられない境界である。戦略予算は、ボラティリティ、流動性、想定ドローダウン、同時稼働戦略との資本配分をもとに、仮説登録時に決める。

戦略のサイズ計算には、固定額、固定リスク、固定ボラティリティなどの方法を使える。ただし、どの方法を選んだか、損失時にサイズをどう扱うか、増額条件と減額条件を、戦略の事前登録に記録する。利益が出たことだけを理由に自動でサイズを増やさない。

## Third-party components

OSSの取引所接続、バックテスター、paper exchange、監視を利用してよい。ただし、外部コンポーネントの出力は未信頼入力として扱い、注文前に当社の決定論的リスク検査を通す。OSSの設定だけで注文上限、キルスイッチ、会計照合を代替しない。

## Non-negotiable controls

注文アダプターへ到達する前に、決定論的なリスクエンジンが最低限以下を検査する。

- 環境と取引モード
- 許可された取引所、口座、銘柄、注文種別
- 価格の鮮度と妥当性
- 1注文、銘柄、口座全体の数量・想定元本
- レバレッジ、証拠金、利用可能残高
- 注文頻度、重複、価格乖離
- 日次損失、累積ドローダウン
- データ、時刻同期、API、照合、監視の健全性
- キルスイッチと手動停止状態

検査不能は拒否とする。リスクサービス停止時に注文を素通ししてはならない。

## Change control

以下は高リスク変更であり、通常の戦略改善と同じPRに混ぜない。

- `live_trading_enabled` の変更
- 注文、ポジション、損失、レバレッジ上限の緩和
- 新しい取引所、口座、銘柄、注文種別
- API権限、秘密情報、ネットワーク到達範囲
- キルスイッチ、照合、監視、リスク検査

高リスク変更には、変更理由、数値根拠、失敗モード、テスト、段階導入、ロールバック、人間の明示承認が必要である。

## Credentials

- 秘密情報はリポジトリ外のSecret Manager等に置く。
- 研究・CI・AIレビューへ本番秘密情報を渡さない。
- 市場データ、照会、取引、資金移動の権限を分離する。
- 取引主体の資格情報に出金権限を付与しない。
- 漏洩の疑いがあれば取引を停止し、失効・再発行・監査を行う。

## Capital allocation

増額は新しい実験として扱う。利益が出たことだけを理由に自動増額しない。観測期間、最大損失、流動性、運用容量、実績と期待値の乖離を再評価し、人間が承認する。
